## 0. КРАТКО (TL;DR)

Платформа-конвейер, которая по ссылке на **iOS-приложение** автоматически:
1. Находит его Android-аналог (поиск в клоне Play Market и на спец-ресурсах APK).
2. Скачивает APK.
3. Прогоняет APK на онлайн-эмуляторе Android: проходит все экраны, кликает, делает скриншоты.
4. Передаёт скриншоты и карту экранов в локальный **Claude Code**, который анализирует
   логику приложения и **генерирует новое приложение на Flutter** (сборка под iOS).
5. Claude Code сам тестирует сборку (в т.ч. в Chrome), итеративно сверяется со скриншотами,
   пока визуальное/функциональное соответствие не достигнет **≥ 95%**.
6. На выходе — готовое протестированное Flutter-приложение, собираемое под iOS.

Всё управляется через **админку**: запуск задач, мониторинг этапов, просмотр скриншотов и
результатов, и **редактирование промптов** Claude Code без правки кода.

Архитектура: **микросервисы + очередь задач**, каждый этап конвейера — отдельный сервис.
Провайдер эмулятора — **подключаемый** (первый — Firebase Test Lab, заменяем без переписывания).
Claude Code — **отдельный worker-процесс на хосте** (локальная установка, авторизация, без API-токенов).

> ⚠ **Правовые ограничения и допущения** — см. §12. Решения по правовому скоупу принимает
> пользователь; команда реализует то, что в скоупе, и не выходит за него без явного указания.

## 1. ЦЕЛИ И НЕ-ЦЕЛИ

### 1.1 Цели
- Автоматизировать путь «ссылка на iOS-приложение → готовое Flutter-приложение под iOS».
- Сделать каждый этап **наблюдаемым и перезапускаемым** (видно, где упало, можно ретраить).
- Дать оператору контроль через админку: запуск, мониторинг, артефакты, промпты.
- Спроектировать ключевые внешние зависимости (эмулятор, кодоген, сборка) как **сменные модули**.

### 1.2 Не-цели (на текущую фазу)
- НЕ публикуем приложения в сторы автоматически.
- НЕ обходим DRM/защиту приложений, НЕ декомпилируем байткод для извлечения исходников
  (работаем по **наблюдаемому поведению**: экраны, навигация, UX — см. §12).
- НЕ поддерживаем генерацию под Android-выход на первой фазе (выход — iOS через Flutter).
- НЕ делаем мультиарендность/биллинг на первой фазе (один оператор/команда).

## 2. ГЛОССАРИЙ
- **Source app** — исходное iOS-приложение (вход конвейера).
- **APK** — Android-пакет найденного аналога source app.
- **Walkthrough** — автоматический обход APK на эмуляторе: клики + скриншоты + карта экранов.
- **Screen map** — структурированная карта экранов/переходов (граф навигации).
- **Generated app** — новое Flutter-приложение, которое создаёт Claude Code.
- **Provider** — сменная реализация внешней способности (эмулятор, кодоген, сборка).
- **Job** — одна сквозная задача клонирования (от ссылки до готового приложения).
- **Stage** — этап конвейера внутри job (discovery, download, walkthrough, codegen, ...).

## 3. АКТОРЫ
- **Оператор** — человек в админке: создаёт jobs, смотрит прогресс/артефакты, правит промпты, ретраит.
- **Конвейер (система)** — оркестратор + микросервисы этапов + очередь.
- **Claude Code worker** — локальный процесс на хосте, выполняет анализ и генерацию приложения.
- **Внешние провайдеры** — клон Play Market, APK-ресурсы, эмулятор (Firebase), Flutter-тулчейн.

## 4. СКВОЗНОЙ СЦЕНАРИЙ (happy path)

```
1. Оператор вводит ссылку/идентификатор iOS-приложения → создаётся Job (статус QUEUED).
2. DISCOVERY: сервис извлекает метаданные iOS-приложения (название, бандл, издатель, иконка,
   категория) и ищет Android-аналог в клоне Play Market.
   - Найден кандидат(ы) → ранжирование по совпадению (имя/издатель/иконка) → выбор лучшего.
   - Не найден → Job статус NEEDS_INPUT, оператор может задать аналог вручную или отменить.
3. ACQUISITION: по найденному аналогу сервис ищет APK на спец-ресурсах и скачивает его.
   - Проверка целостности (хеш, валидный APK, версия). Несколько источников → fallback.
4. WALKTHROUGH: APK уходит в emulator-сервис через провайдер (Firebase).
   - Провайдер ставит APK на эмулятор, обходит экраны: кликает интерактивные элементы,
     делает скриншот каждого экрана, строит screen map (граф переходов).
   - Артефакты (скриншоты + screen map + логи) сохраняются локально, привязаны к Job.
5. ANALYSIS+CODEGEN: артефакты передаются Claude Code worker’у.
   - Claude Code анализирует экраны и логику; решает, нужны ли админка/контент для ЭТОГО
     приложения; продумывает бизнес-логику и логику приложения целиком.
   - Генерирует Flutter-приложение, итеративно сверяясь со скриншотами.
   - Сам тестирует сборку (Chrome/Flutter), правит, пока соответствие ≥ 95%.
6. DELIVERY: готовое Flutter-приложение (исходники + сборка под iOS) сохраняется как артефакт
   Job, статус DONE. Оператор видит результат и отчёт о соответствии в админке.
```

Каждый переход между этапами идёт **через очередь** и фиксирует статус; падение этапа →
RETRYABLE/FAILED с диагностикой, ретрай из админки.

## 5. ЭТАПЫ КОНВЕЙЕРА (микросервисы) — детальные требования

> Архитектура: каждый этап — **отдельный сервис**, общается через **очередь задач** и
> общее хранилище артефактов. Сервисы не зовут друг друга синхронно по цепочке; они
> публикуют результат этапа, оркестратор двигает Job дальше. Это даёт изоляцию, ретраи и
> горизонтальное масштабирование «узких» этапов (walkthrough, codegen).

### 5.1 Orchestrator (ядро конвейера)
- Управляет жизненным циклом Job и последовательностью Stage.
- Состояния Job: `QUEUED → DISCOVERY → ACQUISITION → WALKTHROUGH → ANALYSIS → CODEGEN → DELIVERY → DONE`,
  плюс `NEEDS_INPUT`, `RETRYABLE`, `FAILED`, `CANCELLED`.
- Каждый Stage идемпотентен: повторный запуск с теми же входами не плодит дубли артефактов.
- Публикует события в очередь; слушает результаты этапов; обновляет статус и таймлайн.
- Хранит таймлайн Job (когда какой этап начат/завершён, длительности, ошибки).

### 5.2 Discovery-сервис (поиск Android-аналога)
- Вход: ссылка/ID iOS-приложения. Извлекает метаданные (имя, издатель, иконка, категория, описание).
- Ищет аналог в **клоне Play Market** (источник конфигурируется в админке).
- Ранжирует кандидатов: совпадение имени, издателя, визуальное сходство иконки, категория.
- Выход: выбранный Android-пакет (package id) + уверенность совпадения + список альтернатив.
- Нет уверенного совпадения → `NEEDS_INPUT` (оператор подтверждает/задаёт вручную).
- **Провайдер-абстракция:** «источник каталога Android-приложений» — сменный (клон Play Market
  сегодня, другой каталог завтра).

### 5.3 Acquisition-сервис (скачивание APK)
- Вход: package id + метаданные. Ищет APK на **спец-ресурсах** (список источников — в админке).
- Скачивает APK, проверяет: валидность пакета, версия, размер, хеш; ведёт несколько источников
  с приоритетом и fallback при недоступности.
- Выход: файл APK в хранилище артефактов + манифест (версия, источник, хеш, дата).
- **Провайдер-абстракция:** «источник APK» — сменный список ресурсов с единым интерфейсом.

### 5.4 Emulator-сервис (walkthrough APK) — отдельный микросервис
- Вход: APK + параметры обхода. Передаёт APK выбранному **провайдеру эмулятора**.
- Провайдер: ставит APK на онлайн-эмулятор Android, проходит экраны — кликает интерактивные
  элементы, обходит вкладки/навигацию, делает **скриншот каждого экрана**, строит **screen map**.
- Сохраняет локально: скриншоты (по экранам), screen map (граф переходов), логи обхода, видео (опц.).
- Стратегия обхода настраивается: глубина, лимит экранов, таймауты, обработка логина/попапов
  (поведение при экранах, требующих ввод — конфигурируется; по умолчанию — пропуск/скриншот).
- **Провайдер-абстракция (ключевое требование):** интерфейс `EmulatorProvider` с методами вида
  `install(apk)`, `walkthrough(strategy) → {screens[], screenMap, logs}`, `teardown()`.
  - Первая реализация: **Firebase Test Lab**.
  - Смена провайдера (другой онлайн-симулятор) — это **новая реализация интерфейса + запись
    в конфиге**, без изменения остального конвейера. Выбор активного провайдера — в админке.
- Результат обхода привязан к Job; повторный обход возможен (другой провайдер/стратегия).

### 5.5 Analysis + Codegen (Claude Code worker) — отдельный worker-процесс на хосте
- **Запуск:** Claude Code установлен **локально на хосте**, авторизован (не API-токены).
  Конвейер взаимодействует с ним через **отдельный worker-процесс на хосте**: оркестратор
  кладёт задачу в очередь → worker забирает → готовит рабочую папку → запускает Claude Code →
  возвращает результат и артефакты в Job.
- **Рабочая папка задачи:** worker создаёт изолированную папку для каждого Job со входными
  артефактами (скриншоты, screen map) и **промптами** (см. §6 — промпты редактируются в админке).
- **Что делает Claude Code (по промптам):**
  1. Анализирует все экраны и навигацию (screen map + скриншоты).
  2. Анализирует логику приложения; решает, **нужна ли админка** и **нужен ли контент** именно
     для этого приложения (не у всех приложений это есть).
  3. Продумывает **всю бизнес-логику и логику приложения** целиком.
  4. Генерирует приложение на **Flutter** (сборка под iOS — на первой фазе; решение сменное).
  5. Итеративно создаёт экраны, **сверяясь со скриншотами**.
  6. **Сам тестирует** сборку (в т.ч. в Chrome), правит, пока соответствие **≥ 95%**.
- **Критерий соответствия (≥ 95%):** должен быть измеримым. Определить метрику (визуальное
  сходство по экранам + покрытие экранов screen map + проход ключевых сценариев). Точная
  формула фиксируется при декомпозиции (открытый вопрос — см. §13).
- **Выход:** исходники Flutter-приложения + результат самотестирования + отчёт о соответствии.
- **Сменность кодогенератора/сборки:** Flutter — выбор первой фазы; интерфейс «кодоген+сборка»
  спроектировать так, чтобы цель сборки (Flutter→iOS) можно было заменить без переписывания
  конвейера. Также заложить будущий ввод **готовых iOS-экранов от дизайнера** (см. §11).

### 5.6 Delivery-сервис
- Собирает финальные артефакты Job: исходники, сборку под iOS, скриншоты-сравнения, отчёт.
- Помечает Job `DONE`, публикует результат в админку (скачивание/просмотр).
- Версионирование: повторный прогон того же source app → новая версия результата, история сохраняется.

## 6. ПРОМПТЫ CLAUDE CODE (редактируемые из админки) — ключевое требование
- Промпты для Claude Code хранятся как **управляемые ресурсы**, редактируются **в админке**
  без правки кода и без передеплоя.
- Организация: **отдельные папки/наборы промптов** по назначению (анализ экранов, решение
  про админку/контент, проектирование бизнес-логики, генерация экранов, цикл самотестирования).
- Версионирование промптов: каждое изменение — новая версия; видно, какой версией промпта
  сгенерирован конкретный Job (воспроизводимость).
- Возможность иметь **наборы промптов под разные стратегии** и выбирать активный набор для Job.
- Worker (§5.5) подкладывает актуальную версию промптов в рабочую папку задачи при запуске.

## 7. АДМИНКА — функциональные требования
- **Аутентификация** оператора (роль admin; ролевую модель можно расширить позже).
- **Jobs:**
  - Создать Job (ссылка/ID iOS-приложения, выбор набора промптов, выбор провайдера эмулятора).

  - Карточка Job: таймлайн этапов, текущий статус, длительности, ошибки.
  - Действия: ретрай этапа, отмена Job, ручной ввод аналога (если `NEEDS_INPUT`).
- **Артефакты:** просмотр скриншотов обхода, screen map (граф), скачивание APK-манифеста,
  просмотр сгенерированного приложения и отчёта о соответствии (≥95%).
- **Промпты (§6):** CRUD наборов/папок промптов, версии, выбор активного набора.

- **Источники (§5.2, §5.3):** управление списком источников каталога Android-приложений и
  APK-ресурсов (приоритеты, вкл/выкл).
- **Мониторинг:** очередь (длина, застрявшие задачи), здоровье сервисов, последние ошибки.
- **Логи/аудит:** кто что менял (промпты, провайдеры, источники), история запусков.

## 8. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
- **Наблюдаемость:** структурные логи по Job/Stage, метрики длительностей этапов, дашборд очереди.
- **Отказоустойчивость:** падение этапа не роняет конвейер; ретраи с backoff; «ядовитые»
  задачи уходят в dead-letter с диагностикой.
- **Идемпотентность** этапов (повторный запуск безопасен — совпадает с RULES bootstrap).
- **Изоляция:** обработка недоверенных APK на эмуляторе изолирована (sandbox провайдера).
- **Конфигурируемость:** провайдеры, источники, промпты, пороги (95%, лимиты обхода) — без редеплоя.
- **Хранилище артефактов:** скриншоты/APK/исходники — локально, с привязкой к Job и версиям.
- **Производительность:** «узкие» этапы (walkthrough, codegen) масштабируются числом воркеров.
- **Безопасность:** секреты провайдеров — вне репозитория (.env/secrets, как в RULES);
  не логировать чувствительное.

## 9. ПРОВАЙДЕР-АБСТРАКЦИИ (сменные модули) — сводно
Все внешние способности — за единым интерфейсом, активная реализация выбирается в конфиге/админке:
- **AndroidCatalogProvider** — поиск аналога (клон Play Market → другие каталоги).
- **ApkSourceProvider** — поиск/скачивание APK (спец-ресурсы, список с приоритетами).
- **EmulatorProvider** — обход APK на эмуляторе (**Firebase Test Lab** — первая реализация).
- **CodegenTarget** — целевая платформа генерации/сборки (**Flutter→iOS** — первая фаза).
- **PromptSet** — набор промптов Claude Code (редактируется в админке, версионируется).

Требование к каждому: добавление новой реализации = новый класс/модуль под интерфейс +
регистрация в конфиге, **без изменения оркестратора и остальных сервисов**.

## 12. ПРАВОВЫЕ ОГРАНИЧЕНИЯ И ДОПУЩЕНИЯ (решает пользователь)
Этот раздел фиксирует ограничения, чтобы команда не выходила за скоуп. Решения по объёму —
за пользователем; здесь — рамки по умолчанию:
- Скачивание APK со сторонних ресурсов, клонирование чужих приложений и обход магазинов
  затрагивают авторские права, ToS магазинов и применимое право. По умолчанию система
  работает по **наблюдаемому поведению** (экраны/навигация/UX), а **не** извлекает чужой
  исходный код, ассеты под защитой или DRM-контент.
- Не встраивать обход технических средств защиты.
- Источники APK/каталогов конфигурируются пользователем под его ответственность; система
  предоставляет механизм, выбор источников — за оператором.

## 13. ОТКРЫТЫЕ ВОПРОСЫ (заполняется командой в SPEC_QUESTIONS.md, решает пользователь)

  решения Claude Code?
- Конкретный стек микросервисов/очереди/хранилища — предложит **architect** (2–3 варианта,
  §3.2 в CREATE.md), пользователь выбирает.
